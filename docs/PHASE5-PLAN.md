# План разработки: Фаза 5

Этот документ содержит детальный план пятой фазы разработки aprover — **Рефакторинг документации МТС**.

## Обзор Фазы 5

Фаза 5 направлена на реорганизацию и структурирование документации Метатеории Связей (МТС) для повышения её доступности, последовательности изложения и удобства обновления по ходу разработки прувера.

### Цель фазы

Создать иерархически организованную, модульную документацию МТС, где каждый раздел:
- Имеет чёткую зону ответственности
- Может обновляться независимо
- Связан с другими разделами через явные перекрёстные ссылки
- Соответствует структуре прувера и его возможностям

### Выявленные проблемы

1. **Дублирование контента**
   - Введение (`00`, `01`, `02`) содержит много перекрёстных повторений
   - Аксиомы описаны минимум в 4 файлах (`04`, `05`, `07`, `13`)
   - Нотации описаны в `07`, `08`, `specification-v0.1.md`

2. **Несогласованность терминологии**
   - В разных файлах используются разные обозначения (`⟼` vs `->`, `-` vs `!`)
   - Некоторые файлы используют устаревшую терминологию

3. **Отсутствие иерархии**
   - Файлы пронумерованы, но не образуют логической иерархии
   - Нет чёткого разделения на "теория" vs "реализация"

4. **Черновики смешаны с финальными документами**
   - `formal-notation.md` — явно черновик
   - `sign-link-gap.md` — философская дискуссия, не документация

5. **Несоответствие коду прувера**
   - Документация не всегда отражает текущую реализацию
   - Нет явных ссылок на код

## Принципы рефакторинга

### 1. Принцип единственного источника правды

Каждая концепция должна быть определена в одном месте. Другие разделы ссылаются на это определение.

**Пример:**
- Аксиома А4 (акорень) определяется в `02-axioms/02-aroot.md`
- В `01-foundations/01-introduction.md` — только краткое упоминание со ссылкой

### 2. Принцип модульности

Каждый файл должен быть самодостаточным и обновляемым независимо.

**Пример:**
- При изменении синтаксиса формальной нотации обновляется только `03-notations/02-formal.md` и `03-notations/05-ebnf.md`

### 3. Принцип согласованности с кодом

Документация должна ссылаться на конкретные файлы и функции в коде.

**Пример:**
```markdown
## Реализация

Аксиома А4 реализована в файле `src/core/prover.ts`:

```typescript
// src/core/prover.ts:42-48
const axiomA4 = {
  name: 'Акорень ∞',
  formula: '∞ : (∞ -> ∞)',
  description: 'Полное самозамыкание'
}
```
```

### 4. Принцип версионирования

Эталонная спецификация должна версионироваться и храниться отдельно.

**Пример:**
- `specification/v0.1.md` — текущая версия
- При значительных изменениях создаётся `specification/v0.2.md`
